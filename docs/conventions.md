# Development conventions

## Goal and first instructions

Work in the user's local Codex environment. The inspected monorepo is `~/sites/mono`, with libraries in `lib/` and bundles in `bu/`; applications are siblings under `~/sites`. Read `~/sites/showcase/CONVENTIONS.md`, its other top-level Markdown context, `~/sites/mono/bu/AGENTS.md` (mirrored by `CLAUDE.md`), and each target repository's applicable instructions and canonical `OVERVIEW.md`/`PLAN.md` before making changes. If launched inside a dev3 managed task, use its existing worktree and task scope; do not create a second checkout or silently edit sibling repositories outside that scope. Create a standalone Composer package `survos/otio`, a thin `survos/otio-bundle`, and a Symfony application at `~/sites/otio-demo`. The user will publish both packages to Packagist; prepare them for publication without publishing on their behalf.

This is a browser player for editorial compositions generated from structured data. It is not a video editor. First prove playback using small, known samples, then integrate archival collections and oral histories. Do not begin with large downloads or AI reconstruction.

Platform conventions specify PHP 8.4+ and Symfony 8.1+, method-level command attributes, Twig, AssetMapper, and Survos packages. The inspected Fotostory composer.json actually requires PHP ^8.5 and Symfony 8.1; confirm each target's runtime and lockfile rather than copying an older baseline. Reuse existing Tabler integration and package-linking tools. Do not modify vendor files or introduce Composer path repositories when existing monolink/bu-install conventions are available.


## Package and application rules


- Put `survos/otio` in `mono/lib/otio` and `survos/otio-bundle` in `mono/bu/otio-bundle`, subject to the monorepo's current naming conventions. “Standalone” means independently installable, not a new unrelated source repository. Register each new package in `.github/workflows/split.yml` **in the same commit as its files**; adding registration later can leave it silently unsplit. Publish the two scaffold repositories now as explicitly requested; leave Packagist registration to the user and do not create stable release tags.
- New bundles require `survos/kit-bundle`; use `Survos\Kit\AbstractUxBundle` for the player UX bundle (or `AbstractSurvosBundle` if UX is split out). Keep `configure()`, `loadExtension()`, and required prepends in `src/SurvosOtioBundle.php`; let kit handle its conventional registrations. Include `#[RequiredBundle(SurvosKitBundle::class)]` and the exact Flex marker immediately above the concrete class: `// Symfony\Component\HttpKernel\Bundle\Bundle <-- Flex auto-registration marker (see Survos\Kit\AbstractSurvosBundle)`. Check the actual kit imports and hooks before copying the skeleton.
- Group commands as method-level `#[AsCommand('otio:validate', 'Validate an OTIO document')]` attributes on a cohesive `OtioService`; never extend `Command` or put `AsCommand` on the class. Constructor-inject dependencies; command methods take console I/O and typed arguments/options/`#[MapInput]` DTOs. Use positional descriptions and `Command::SUCCESS`, `FAILURE`, or `INVALID`. Explicitly register the service family if kit's directory convention does not cover `src/Service/`.
- UX names derive from the complete Composer name: `@survos/otio-bundle` in assets/package.json and controllers.json; keep `-bundle`. Set Composer `keywords` to include `symfony-ux`. Use `survos_stimulus('otio-bundle', 'player')` with Twig's stimulus helpers, without controller-name overrides or literal data-controller strings.
- Use camelCase for Survos metadata/profile and runtime projection keys. **Preserve OTIO's upstream keys exactly**, including `OTIO_SCHEMA`, `source_range`, and `media_reference`; they are externally defined data, not platform naming violations.
- Keep the core free of framework dependencies as requested. Use Symfony components and platform libraries in the bundle/application for I/O, validation and integration. If JSONL is needed there, use `survos/jsonl-bundle`; byte-size display uses `zenstruck/bytes`.
- Use Tabler's existing menus/page actions; do not render a second action bar. Entity-backed routes use field-bundle `RouteIdentity`/`RouteIdentityTrait` and `.rp`; no entity boilerplate or hard-coded identity maps. Filesystem sample DTOs need not become Doctrine entities just for routing.
- AssetMapper remains the app asset system; any JSX build is a localized player build step, not an Encore migration. If browser route generation is needed, use js-twig-bundle's routing integration, not FOSJsRouting. Reuse existing search/grid UI only when needed; the small sample gallery does not need a new search engine.
- Supply `OVERVIEW.md` and `PLAN.md` in each new component so showcase can ingest them. Showcase points to canonical docs; it is not their storage location. Historical README commands are not authority over newer conventions or current code.
